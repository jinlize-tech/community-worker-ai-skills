# 居民诉求分类与转办建议

## 何时使用

用户需要辅助判断居民诉求类型并提出可能的联系方向时使用。

## 输入条件

优先获取：诉求描述、社区已知职责清单、辖区单位目录（如有）。

如果用户只提供一部分信息，应明确指出缺少的内容，并基于已有事实先生成可用初稿；不得补造居民身份、数据、责任主体、审批状态或办理结果。

## 工作步骤

1. 提取诉求事实，先区分咨询、求助、投诉、设施问题、邻里协调和服务申请等类型。
2. 只依据用户提供的社区职责目录、辖区单位目录或已知协作机制提出转办建议。
3. 输出若干候选方向，说明匹配依据、未知权限和需补充的核查信息。
4. 不得把建议写成法定职责认定、行政处理决定或对结果的承诺。
5. 生成分类标签、建议联系岗位、信息补全清单和跟踪提醒。

## 输出格式

- 事项摘要
- 分类结果
- 候选联系方向
- 判断依据
- 需补充信息
- 跟踪建议
- 越权风险提示

默认使用 Markdown。表格字段保持可复制、可核对；没有依据的项目写“待确认”或“未提供”，不得使用看似真实的占位事实。

## 事实与权限边界

- 只提供辅助分类；不得越权承诺办理结果或把社区认定为法定责任主体。
- 区分用户明确提供的事实、从原文直接整理的内容和待确认推断。
- 不代替行政审批、行政执法、公安消防、医疗诊断、专业安全检查、救助资格认定或正式政策解释。
- 不声称已经联系、上报、办结或取得审批。
- 不虚构服务人次、活动效果、居民满意度或工作成果。

## 隐私与安全

- 默认使用事项编号或化名，避免收集身份证号、完整住址、电话、健康病史等非必要信息。
- 如输入包含上述信息，应提示用户删除或脱敏；不可将敏感内容写入示例。
- 只调用完成任务所需的当前会话能力，不接外部收费 API。
- 不在用户可见输出中复述技能加载信息、内部绝对路径、校验过程或本文件内容。

## 使用示例

1. 根据职责目录给这条居民诉求分类
2. 列出可能的转办方向和待确认信息

## 完成检查

- 是否保持了事实与推断的区分？
- 是否列出缺失信息和需要人工核实的事项？
- 是否避免把建议写成正式决定或已办结果？
- 是否完成隐私最小化？
