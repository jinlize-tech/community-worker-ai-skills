# 楼栋/网格事项交接清单

## 何时使用

用户需要轮班交接或跨网格移交事项时使用。

## 输入条件

优先获取：事项台账、交接笔记。

如果用户只提供一部分信息，应明确指出缺少的内容，并基于已有事实先生成可用初稿；不得补造居民身份、数据、责任主体、审批状态或办理结果。

## 工作步骤

1. 用事项编号或化名标识事项，删除不必要的居民身份信息。
2. 提取当前状态、已完成动作、责任联系岗位、下一次跟进时间和阻塞原因。
3. 区分需要接班人员立即处理、可以等待和只需知晓的事项。
4. 为每个事项记录交接依据和未确认信息，不把口头承诺写成正式决定。
5. 生成交接清单、优先跟进事项、缺失信息和双方确认项。

## 输出格式

- 交接范围
- 事项清单
- 优先跟进
- 已联系对象
- 下一步动作
- 风险和依赖
- 待确认信息
- 交接确认项

默认使用 Markdown。表格字段保持可复制、可核对；没有依据的项目写“待确认”或“未提供”，不得使用看似真实的占位事实。

## 事实与权限边界

- 使用事项编号替代居民身份信息；不得传播无关个人资料。
- 区分用户明确提供的事实、从原文直接整理的内容和待确认推断。
- 不代替行政审批、行政执法、公安消防、医疗诊断、专业安全检查、救助资格认定或正式政策解释。
- 不声称已经联系、上报、办结或取得审批。
- 不虚构服务人次、活动效果、居民满意度或工作成果。

## 隐私与安全

- 默认使用事项编号或化名，避免收集身份证号、完整住址、电话、健康病史等非必要信息。
- 如输入包含上述信息，应提示用户删除或脱敏；不可将敏感内容写入示例。
- 只调用完成任务所需的当前会话能力，不接外部收费 API。
- 不在用户可见输出中复述技能加载信息、内部绝对路径、校验过程或本文件内容。

## 使用示例

1. 把换班记录整理成交接清单
2. 挑出接班人员今天必须处理的事项

## 完成检查

- 是否保持了事实与推断的区分？
- 是否列出缺失信息和需要人工核实的事项？
- 是否避免把建议写成正式决定或已办结果？
- 是否完成隐私最小化？
