# 居民诉求接待记录整理

## 何时使用

用户需要将居民来电、来访或口头诉求整理成标准接待记录时使用。

## 输入条件

优先获取：脱敏后的居民诉求记录、接待笔记。

如果用户只提供一部分信息，应明确指出缺少的内容，并基于已有事实先生成可用初稿；不得补造居民身份、数据、责任主体、审批状态或办理结果。

## 工作步骤

1. 先提醒用户使用化名或事项编号，移除身份证号、完整门牌号和不必要联系方式。
2. 提取居民原意、发生地点范围、涉及对象、希望解决的问题和已提供的信息。
3. 记录社区已告知事项和已采取动作，明确这是记录而非处理决定。
4. 将未经证实的内容标为“待核实”，不自行认定责任主体或办理结果。
5. 输出标准接待记录、待核实问题和下一步建议。

## 输出格式

- 事项编号与接待信息
- 居民诉求摘要
- 事实与证据
- 已告知事项
- 待核实问题
- 后续动作
- 隐私提示

默认使用 Markdown。表格字段保持可复制、可核对；没有依据的项目写“待确认”或“未提供”，不得使用看似真实的占位事实。

## 事实与权限边界

- 默认使用编号或化名；不收集身份证号、完整住址、联系方式等非必要信息。
- 区分用户明确提供的事实、从原文直接整理的内容和待确认推断。
- 不代替行政审批、行政执法、公安消防、医疗诊断、专业安全检查、救助资格认定或正式政策解释。
- 不声称已经联系、上报、办结或取得审批。
- 不虚构服务人次、活动效果、居民满意度或工作成果。

## 隐私与安全

- 默认使用事项编号或化名，避免收集身份证号、完整住址、电话、健康病史等非必要信息。
- 如输入包含上述信息，应提示用户删除或脱敏；不可将敏感内容写入示例。
- 只调用完成任务所需的当前会话能力，不接外部收费 API。
- 不在用户可见输出中复述技能加载信息、内部绝对路径、校验过程或本文件内容。

## 使用示例

1. 把这段居民来访笔记整理成标准记录
2. 提取诉求中的事实和待核实信息

## 完成检查

- 是否保持了事实与推断的区分？
- 是否列出缺失信息和需要人工核实的事项？
- 是否避免把建议写成正式决定或已办结果？
- 是否完成隐私最小化？
