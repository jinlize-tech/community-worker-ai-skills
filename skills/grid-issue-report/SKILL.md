# 网格巡查问题上报单

## 何时使用

用户需要把网格巡查中的客观发现整理为问题上报材料时使用。

## 输入条件

优先获取：现场观察记录、脱敏地点描述、图片说明（如有）。

如果用户只提供一部分信息，应明确指出缺少的内容，并基于已有事实先生成可用初稿；不得补造居民身份、数据、责任主体、审批状态或办理结果。

## 工作步骤

1. 确认发现时间、地点范围、观察主体、现场现象和已有证据。
2. 使用中性、可验证的描述，不使用“违法”“责任人明确”等未经认定的结论。
3. 区分直接观察、居民转述和待核实推断，保留照片或记录的来源说明。
4. 补充影响范围、临时安全措施、建议联系方向和待补证据。
5. 输出问题上报单、优先级提示和跟进状态，便于人工审核。

## 输出格式

- 问题标题与编号
- 发现时间地点
- 客观现象
- 已知影响
- 照片/证据说明
- 已采取临时措施
- 建议报告方向
- 待核实信息

默认使用 Markdown。表格字段保持可复制、可核对；没有依据的项目写“待确认”或“未提供”，不得使用看似真实的占位事实。

## 事实与权限边界

- 只记录客观观察，不自行认定违法或安全责任；依法由有权部门处置。
- 区分用户明确提供的事实、从原文直接整理的内容和待确认推断。
- 不代替行政审批、行政执法、公安消防、医疗诊断、专业安全检查、救助资格认定或正式政策解释。
- 不声称已经联系、上报、办结或取得审批。
- 不虚构服务人次、活动效果、居民满意度或工作成果。

## 隐私与安全

- 默认使用事项编号或化名，避免收集身份证号、完整住址、电话、健康病史等非必要信息。
- 如输入包含上述信息，应提示用户删除或脱敏；不可将敏感内容写入示例。
- 只调用完成任务所需的当前会话能力，不接外部收费 API。
- 不在用户可见输出中复述技能加载信息、内部绝对路径、校验过程或本文件内容。

## 使用示例

1. 把巡查发现整理成问题上报单
2. 区分现场观察和待核实推断

## 完成检查

- 是否保持了事实与推断的区分？
- 是否列出缺失信息和需要人工核实的事项？
- 是否避免把建议写成正式决定或已办结果？
- 是否完成隐私最小化？
