# 网格走访记录整理

## 何时使用

用户需要整理日常网格走访、楼栋联络或居民服务记录时使用。

## 输入条件

优先获取：脱敏走访笔记、事项编号、走访目的。

如果用户只提供一部分信息，应明确指出缺少的内容，并基于已有事实先生成可用初稿；不得补造居民身份、数据、责任主体、审批状态或办理结果。

## 工作步骤

1. 确认走访日期、范围、目的和参与人员，提醒移除居民姓名、完整门牌号和联系方式。
2. 提取居民主动提出的需求、现场观察、已提供帮助和需协调事项。
3. 区分客观观察、工作人员判断和居民原话，保留必要的来源标注。
4. 不生成敏感人群标签、健康推断或未经授权的风险分级。
5. 输出脱敏走访记录、服务事项和后续联系提醒。

## 输出格式

- 走访概况
- 现场观察
- 居民主动需求
- 已提供帮助
- 需协调事项
- 后续提醒
- 脱敏检查

默认使用 Markdown。表格字段保持可复制、可核对；没有依据的项目写“待确认”或“未提供”，不得使用看似真实的占位事实。

## 事实与权限边界

- 仅记录与服务有关的必要信息；不得形成无授权的敏感人群标签。
- 区分用户明确提供的事实、从原文直接整理的内容和待确认推断。
- 不代替行政审批、行政执法、公安消防、医疗诊断、专业安全检查、救助资格认定或正式政策解释。
- 不声称已经联系、上报、办结或取得审批。
- 不虚构服务人次、活动效果、居民满意度或工作成果。

## 隐私与安全

- 默认使用事项编号或化名，避免收集身份证号、完整住址、电话、健康病史等非必要信息。
- 如输入包含上述信息，应提示用户删除或脱敏；不可将敏感内容写入示例。
- 只调用完成任务所需的当前会话能力，不接外部收费 API。
- 不在用户可见输出中复述技能加载信息、内部绝对路径、校验过程或本文件内容。

## 使用示例

1. 把网格走访笔记整理成标准记录
2. 提取现场观察和居民主动需求

## 完成检查

- 是否保持了事实与推断的区分？
- 是否列出缺失信息和需要人工核实的事项？
- 是否避免把建议写成正式决定或已办结果？
- 是否完成隐私最小化？
